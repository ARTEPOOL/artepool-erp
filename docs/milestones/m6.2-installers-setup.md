## Goal (in plain words)

After M6.2, the system is installed like any Windows program:

1. **Server setup** on the POS PC (it is also the server, 0085). The installer:
   - installs the database and the program;
   - creates the security certificates and the secret keys;
   - opens only the program's port to the shop network;
   - makes everything start by itself with Windows and restart if it stops.
2. **First run:** the program opens a one-time wizard with two choices:
   - **New setup:** company → owner → phone 2-step → recovery codes → this PC becomes the POS.
   - **Restore from backup** (a new PC after loss or damage):
     - choose a copy from this PC, a USB drive or Google Drive;
     - enter the private backup key;
     - the copy is restored and checked;
     - the other PCs are enrolled again.

   Either way the wizard then locks itself for good.
3. **Upgrades** keep everything. Before the new version touches the database, a backup is made and checked. The database changes are all-or-nothing: if anything fails, nothing changes and the old version keeps working.
4. **Uninstall** removes the program but **keeps the data**. Deleting the data needs a separate choice, the owner's password and typing DELETE.
5. **Office setup** for the owner's laptop: the program alone (M6.5 enrolls it).
6. **System health** also reminds about:
   - the UPS;
   - the last backup;
   - the backup key;
   - disk space;
   - the services;
   - the certificate's expiry.

## What exists today, and what M6.2 adds

| Exists | Missing (added in M6.2) |
|---|---|
| Console tools `owner:create`, `device:code`, resets (0025) | A packaged server (`build:server`): one Node runtime + one bundled file, no developer tools on the PC |
| TLS CA and server certificate tool (`tls:init`), name-constrained | Created by the installer with the PC's **name and fixed LAN address** |
| Master key as a plain file (dev) | The master key and database passwords **protected by Windows (DPAPI, machine scope)**, readable only by the services and administrators |
| Server listens on 127.0.0.1 (dev) | Listens on the LAN; the Windows firewall allows the API port **from the local subnet only** (0093) |
| Backups: hourly copy, Google Drive, external drive, restore **test** | **WAL archiving** + nightly base backup (point-in-time restore, 0086); a **real restore** into the live database (wizard path 2); the backup service as a Windows service |
| No setup state | `sys.setup_state` (one row, `not_started` → `complete`, never back) and the wizard endpoints, answering only on the server PC with the installer's one-time setup token |
| No clock guard (planned in the schema) | `sys.clock_guard()`: writes refused when the server clock goes backwards |
| Kiosk app, no watchdog | Starts with Windows on the POS PC; a watchdog brings it back and reports `restarted` / `not_running` (0082, 0083) |
| Device key in the Windows user's Credential Manager | On the POS PC, the device is stored **for the whole PC** (DPAPI machine scope, ACL), so the cashier's Windows account (M6.4) and the owner's use the same enrolled PC |
| Updater with an empty key (no update accepted) | The updater key is set (private key offline with the owner, 0007); updates are served by the server PC on the LAN |
| Health: backups, key, Drive, integrity, backup-disk space | UPS confirmation (again every 6 months), service status, database and system disk space, certificate expiry |

### Part B — The packaged server — done

**Done (2026-10-20):** `pnpm build:server`, `server.json`, `resourcePath()`, the launcher `artepool-svc` with `run` / `secrets init|set|check`, CI on Linux and Windows. The pinned `node.exe` (SHA-256 checked) is added when the installer is assembled (Part F), since only the installer ships it.

- **`pnpm build:server`:**
  - esbuild bundles `apps/server`, `apps/backup` and the console tools (`owner:*`, `device:code`, `migrate`) into `dist/server/`;
  - a pinned Node 24 runtime (`node.exe`, SHA-256 checked at build time) sits next to them.
- **Configuration:** one file, `C:\ProgramData\ARTEPOOL\config\server.json`:
  - settings: address, port, data paths, Google registration ID;
  - no secrets in it;
  - read by the server, the backup service and the console tools instead of `.env`. Development keeps `.env`.
- **Secrets:** `C:\ProgramData\ARTEPOOL\secrets\`:
  - the master key and the 4 database role passwords, each **DPAPI-protected (LocalMachine)**; since E2 also PostgreSQL's superuser password, given only to the restore program;
  - the folder's ACL allows only SYSTEM, Administrators and the service accounts.
- **Launcher (`artepool-svc.exe`, Rust, small):**
  - unprotects the secrets in memory and starts `node.exe` with them as environment variables;
  - nothing is written to disk in clear;
  - WinSW runs this launcher as the service.
- **Tests:**
  - the bundle starts and answers `/health`;
  - no `.env` and no plain secret is read in production mode;
  - DPAPI round trip on the Windows runner;
  - the launcher refuses to start when a secret file is missing or the ACL is too open.

### Part C — Database: setup state, clock guard (migration 0043) — done

**Done (2026-10-22):** as below. The clock guard compares with the **latest audit row** (every write is audited), so it needs no extra counter that every write would have to lock; it uses the real time of each write (`clock_timestamp()`), so a long transaction is never refused by mistake. **Clock set forward by mistake, then corrected (owner, 2026-10-22):** no emergency command. Writes stay refused until the real time passes the wrong time again, then everything works by itself.

- **`sys.setup_state`** (one row): `state` (`not_started` | `in_progress` | `complete`), `path` (`new` | `restore`), `started_at`, `completed_at`, `installation_id`.
  - A trigger allows only forward moves: `not_started` → `in_progress` → `complete`, never back.
  - The row cannot be deleted.
  - Audited as SYSTEM with "setup wizard".
- **Existing databases** (the shop's when upgrading later, and every database that already has an owner) are marked `complete` by the migration itself, so no wizard ever appears on them.
- **`sys.clock_guard()`:**
  - keeps the highest server time seen;
  - a write whose `now()` is more than 2 minutes before it is refused (`CLOCK_BACKWARDS`) and an alert is raised;
  - the health screen says "the server clock went back: check the Windows time";
  - fixed by correcting the clock; nothing can be posted in the past.
- **Tests:**
  - the state never goes back, the row cannot be deleted, an existing database is `complete`;
  - the clock check refuses writes when the clock goes back and allows normal drift;
  - the privileges test still passes.

### Part D — The setup wizard, path 1: "New setup" — done

**Done (2026-10-22):** as below. The app opens the wizard by itself when the setup token is readable on this PC (no `--setup` flag needed), so closing the app halfway picks up where it stopped. The installer (part F) must leave `setup\ca.crt` next to the token. Development: `pnpm dev:setup-token`.

- **Server, `/api/v1/setup/*`:** answers only when `setup_state` is not `complete` **and** the request comes from the PC itself (127.0.0.1/::1) **and** carries the one-time setup token. The installer writes the token to `ProgramData\ARTEPOOL\setup\token`, readable by Administrators only, and deletes it at the end. Steps:
  1. company details (existing rules);
  2. the owner account (existing rules: name, username, 10+ character password);
  3. phone 2-step (existing screens) and the 10 recovery codes, confirmed;
  4. enroll this PC as **POS**: the server makes a code and the app runs the normal enrollment protocol with it (0024), so the PC is stored as a POS device;
  5. `complete`: the token is deleted and the wizard is locked for good.

  Each step is audited. A step can be repeated until `complete`; after that everything answers "setup is already done".
- **App:** the installer starts the app with `--setup`. The app reads the token and the CA certificate from ProgramData, connects to `https://127.0.0.1:<port>` and shows the wizard. The wizard reuses the existing screens: company form, 2-step setup, recovery codes.
- **Tests:**
  - every endpoint refuses: without the token, from another address, after `complete`, a second owner;
  - a full run gives the owner, 2-step and a POS device;
  - unit and browser tests of the wizard screens in Arabic and English.

### Part E — The setup wizard, path 2: "Restore from backup"

**E1 done (2026-10-22):** the off-site copy is now a bundle (database copy + master key) encrypted for the owner's backup key (`apps/backup/src/bundle.ts`); older copies and the external drive's plain copies still open, without a master key; `pnpm backup:open` for the manual emergency path.

**E2 done (2026-10-24):** the restore engine (`apps/backup/src/full-restore.ts`) and the restore program (`artepool-svc run restore <copy>`, `apps/server/src/cli/restore.ts`; private key on the standard input, progress and result as JSON lines for the wizard). The services are stopped and started by service name `ArtepoolServer` / `ArtepoolBackup` (Part F must use these names). After the swap the restored data's own setup state (complete) keeps the wizard locked; the restore is recorded in the audit log as `system.restored_from_backup`. Next, E3: the wizard screens.

**E3 done (2026-10-24):** the wizard's restore screens (`apps/desktop/src/features/setup/RestoreFlow.tsx`): copies found by the PC's native side on USB drives (and their `ARTEPOOL-BACKUPS` folder), in Downloads, Desktop, Documents and `ProgramData\ARTEPOOL\backups`, or a typed path; the private key typed or loaded from the key file (it goes only to the restore program's input); the steps while it runs; the result; then this PC is enrolled as the POS with the restore's code. The Windows app starts `C:\Program Files\ARTEPOOL\artepool-svc.exe run restore <copy>` (Part F must put the launcher there). A Google Drive copy is downloaded first in the browser (0102 amended). Owner's guide: `docs/runbooks/restore-on-new-pc.md`.

- **Choosing the copy:**
  - from this PC or a USB drive (`.dump` or `.dump.age`, or the `ARTEPOOL-BACKUPS` folder of the external drive);
  - or Google Drive: *(changed 2026-10-24, 0102 amended)* the copy is downloaded from drive.google.com in a browser first, then chosen like a USB copy.
- **The private key:** typed, or loaded from the USB key file. It decrypts an `.age` copy in memory. A wrong key gets a plain "this key does not open this copy".
- **Restoring:**
  - the copy is restored into a new database `artepool_restoring`;
  - then the integrity checks run: audit chain, the copy's anchor, journals balanced, trial balance, stock vs ledger, numbering;
  - **only if all pass**, the restored database replaces the empty new one (services paused for the swap).
  - Then a fresh backup and a restore test.
- **After the restore:**
  - every PC enrolled on the old server is marked "enroll again" (the old PCs trust the old certificate);
  - the owner signs in with their old password and 2-step;
  - the owner makes enrollment codes in Settings → Devices and enters them on each PC (as in 0024);
  - the Google Drive connection is made again; the backup key stays the same.
  - The wizard is locked (`complete`, path `restore`).
- **Keeping 2-step working after a restore:** see question 1. The 2-step secrets in the database are sealed with the server's master key.
- **Tests:**
  - restore of a real copy into a fresh database passes the checks;
  - a wrong key, a damaged copy or a copy whose audit chain was changed are refused, and nothing is replaced;
  - after the restore the old devices cannot connect, and new enrollment works;
  - the wizard is locked afterwards.

### Part G — Upgrades, uninstall and automatic online updates (0103, 0108)
On branch `m6-upgrades`, one commit per step:

- **G1 — All-or-nothing migrations — done.** `pnpm db:migrate --all-or-nothing`: the checksums of applied migrations are verified first, then every pending migration runs in **one** transaction; any failure leaves the database exactly as it was.
- **G2 — Upgrade (a newer server installer on an installed server PC):**
  1. it detects the installation and keeps `ProgramData` as it is;
  2. stops the app and the services;
  3. makes a **pre-upgrade backup**, checked with `pg_restore --list` and its SHA-256, to `backups\pre-upgrade\`;
  4. replaces the program files, keeping the previous version's folder;
  5. runs the new migrations **all-or-nothing** (G1);
  6. starts the services and waits for `/health`.

  If step 5 or 6 fails: nothing changed in the database; the previous version is put back and started; the upgrade log says which step failed and where the pre-upgrade backup is. An older version never installs over a newer one.

  **Built:** `artepool-svc run upgrade prepare|apply` (`apps/server/src/cli/upgrade/`), the setup's upgrade mode (`ARTEPOOL.new` → `ARTEPOOL`, previous kept as `ARTEPOOL.previous`, a failed one as `ARTEPOOL.failed`; exit code 5 = nothing changed, 6 = previous version back), `updates\last-result.json` for System health, the last 10 pre-upgrade copies kept. If the new version does not answer after its migrations, the database is put back from the pre-upgrade copy (the upgraded one kept aside). An open shift stops the upgrade before anything changes.
- **G3 — Uninstall and reinstall:**
  - removes the program, the services, the scheduled task and the firewall rule;
  - **keeps** `C:\ProgramData\ARTEPOOL` (database, backups, secrets, settings);
  - a reinstall finds the data and simply starts again (no wizard).

  **Built:** the setup's reinstall mode (`run install --reattach`): the secrets must open on this PC; the same database, settings and CA (the PCs keep trusting it); a checked copy `…-before-reinstall.dump` first, then the migrations all or nothing; the finished first-run setup stays closed. `config\version.txt` records the version the data belongs to: an older setup never reinstalls over newer data (exit code 4).
- **G4 — Deleting the data:** a separate, unticked choice in the uninstaller:
  - it asks for the **owner's password** (checked by the server against the database, audited) and then for typing `DELETE`;
  - only then are `pgdata`, `wal` and `secrets` removed;
  - the **backups folder is kept**.

  **Built:** `artepool-svc run delete-data` (its own window, opened from the uninstaller's unticked "Also delete the data" page; never in a silent uninstall): DELETE, then the owner's password checked against the database (refusal and confirmation audited, and in `logs\install\delete-data-*.log`); then the services stop and `pgdata`, `wal`, `secrets`, `config`, `setup`, `updates` go. Backups and logs stay.
- **G5 — Automatic online updates (0108):**
  - **Release workflow** (`.github/workflows/release.yml`), started from a version tag on `main`:
    - builds on Windows; runs in the protected **`release` environment** (the owner's one-click approval, `main` only);
    - signs with the update key (environment secrets `TAURI_SIGNING_PRIVATE_KEY` and its password);
    - writes `latest.json` (version, release notes in Arabic and English from `release-notes/<version>.{ar,en}.md`, files, signatures) and `SHA256SUMS.txt`;
    - **publish check:** only `ARTEPOOL-Server-Setup-*.exe`, `ARTEPOOL-Office-Setup-*.exe`, `*.sig`, `latest.json` and `SHA256SUMS.txt` may be published; anything else stops the release;
    - publishes them as a GitHub Release in the public `ARTEPOOL/artepool-releases` with a fine-grained token limited to that repository (environment secret `RELEASES_TOKEN`).
  - **Server PC updater** (`artepool-svc update …`, a scheduled task running as SYSTEM):
    - checks `latest.json` a few times a day; no internet → nothing happens, it tries again later;
    - downloads in the background into `ProgramData\ARTEPOOL\updates`, verifies the signature with the public key built into the program and the SHA-256; refuses older versions;
    - installs only at a **safe time**: no open shift; a fresh backup checked first; inside the night window (setting, default 02:00–05:00) or at once after **Install now**;
    - runs the G2 upgrade; the result (version, time, ok / failed step) is saved for System health.
  - **Other PCs:** the desktop app's updater (the public key in `tauri.conf.json`) reads the public `latest.json`; when the internet is not reachable from that PC, it asks the server PC, which serves the copy it already downloaded. It installs when the app is not in use (never during a sale, never with an open shift on that PC).
  - **System health (owner):** current version; an available update with its release notes; last update result; **Install now**.
  - **USB fallback (support only):** running the newer server installer by hand does the same G2 upgrade.

  **Built:** the release workflow and its publish check (`tools/release`, `.github/workflows/release.yml`); the update signature check in Node (Tauri signer format); migration 0044 (`ops.update_state`, `ops.update_requests`, `system.update.manage`); `artepool-svc run updater` with its scheduled task; the updates API; the System health "Updates" card (notes in the screen's language, waiting reason, last result, "Install now" with a confirmation, night window); the office app updater (installs by itself on the sign-in screen, otherwise "Install and restart"; never on the server PC, whose app comes with the server setup). **Not yet:** the office PCs taking the update from the server PC when they have no internet themselves (they wait for the internet instead; the shop's PCs share one connection, so this is rare) — a later step.
- **G6 — Guides and PR:** `docs/runbooks/updates-setup.md` (the owner's one-time GitHub steps, in Arabic), `upgrade-and-uninstall.md`; PRD, CLAUDE.md and CHANGELOG.
- **Tests:**
  - unit and integration: the safe-time rules (open shift, backup, window, Install now), the signature and version checks, the publish check, the update state;
  - Windows runner: install v1, add data, upgrade to v2 (data kept, migrations applied); a broken migration in v2 (database unchanged, v1 running again); uninstall then reinstall (data back, no wizard); delete-data with a wrong password (nothing deleted) and the right one (database gone, backups kept).

### Part H — System health additions
The owner's health screen, and the dashboard alerts when something needs attention:
- **UPS:** "Is a UPS connected to the server PC?" The owner confirms (date saved). The reminder comes back after 6 months, or at once if not confirmed (0085).
- **Last backup:** already shown, now also on the first line with its age.
- **Backup key created:** already known; shown as its own line with "Create the backup key" if missing.
- **Disk space:** the database disk and the system disk as well as the backups disk.
  - Warning under 10% or 10 GB free; urgent under 5% or 2 GB.
- **Services:** database, server and backup service running. The backup service reports a heartbeat each minute; the screen also shows whether WAL archiving is working.
- **Certificate:** the server certificate's expiry. Reminder 60 days before, with the one-command renewal in the runbook.
- **Clock:** an alert if the server clock went backwards (part C).
- **Tests:** each warning appears and clears (unit and integration); owner only.

  - Owner-only `system.health.manage`.
  - Alert types `ups_unconfirmed`, `disk_low`, `disk_urgent`, `service_down`, `wal_archive_failed`, `certificate_expiring`, `certificate_renewal_failed`, `root_ca_expiring`.
  - The UPS reminder is a fixed 182 days, not a setting.
- **H2 — `GET /api/v1/system/server-health`** (owner) and **`POST …/server-health/ups`** (`system.health.manage`, audited):
  - **Disks:** the data folder, the backups folder and the system drive. Warning under 10% or 10 GB free, urgent under 5% or 2 GB.
  - **Backup service:** it writes `backups\.heartbeat` every minute on its own timer. Older than 5 minutes means "not running".
  - **WAL archiving** from `pg_stat_archiver`.
  - **Server certificate:** orange from 60 days, red from 14.
  - **Root CA:** orange from two years, red from six months.
  - **Clock** and **UPS**.
  - The server's 5-minute check raises one alert per problem per day.
- **H3 — Automatic renewal** by the SYSTEM updater task (`apps/server/src/cli/updater/certificate.ts`):
  - **When:** from 60 days before the end, at night (the update window), with no open shift, at most once a day, and never during an update.
  - **What:** a new two-year certificate from the same root CA, for the same names.
  - **Before switching:** a local TLS 1.3 check (`checkServerPair`).
  - **Switching:** the old files are kept as `*.previous`; the server restarts and `/health` must answer with exactly the new certificate.
  - **On failure:** the old files go back and the server restarts again.
  - **Record:** each renewal and failure is written to `ops.server_health`, which the audit log tracks with old and new values.
- **H4 — "Server PC" card** at the top of System health:
  - one line each: last backup with its age, backup key (create it), disks, services and WAL, server certificate, root CA, clock, and UPS ("Yes, a UPS is connected");
  - each line is green, orange or red, in Arabic and English;
  - the owner dashboard's system health card lists the server problems too.
- **H5 — Tests and docs:**
  - unit: disk, certificate and UPS rules, the heartbeat, the alerts, and the TLS helpers;
  - integration: the API, the renewal (due, waiting, renewed and audited, refused check, rollback, once a day) and the database rules;
  - desktop: the card and the UPS confirmation;
  - screens: the card in both languages;
  - docs: the schema doc §12.7 and the CHANGELOG.
